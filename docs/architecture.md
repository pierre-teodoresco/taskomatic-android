# Android architecture

Taskomatic has no deadlines: a task stays active until explicitly completed. Simple completed tasks are archived; recurring tasks return at the start of the local day N calendar days, weeks or months after completion. Months clamp to the last valid day and missed cycles do not accumulate.

The pure Kotlin `core` module receives an `Instant` and `ZoneId`. UUID cycle tokens protect later task cycles from old notification actions. Tests use fixed dates, including Paris daylight saving and Santiago's midnight transition.

The Android adapter persists tasks in a private SQLite database. Mutations read fresh state and only replace their owned fields. Recurrence edits preserve active state while respecting completion after the editor opened. Restores/imports rotate cycle tokens. Saves precede reminder scheduling; errors are reported without discarding the user's editor draft.

SQLite projections read at most 128 KiB of each title/note per row, then assemble any remaining BLOB fragments before UTF-8 decoding. This keeps valid large imports readable on API 26+ without exceeding CursorWindow or truncating embedded NUL/Unicode. Typical short fields need no extra queries. Preferences use a separate single-row SQLite database; failed writes leave the previous values visible and durable.

Small editor state stays in SavedState; strings longer than 8,192 UTF-16 code units use private atomic files referenced by short keys. Originals and edited drafts are kept separately so restoration cannot change stale-editor merge semantics. Quick drafts and editor recovery files are removed when explicitly consumed/closed. Recovery failures show a warning and never alter the persisted task. Bounded visible text-field height allows long notes to scroll without exceeding Compose layout constraints. These recovery files are local, not portable backups.

Reminders use the system alarm and notification APIs, with local weekday/time settings. Android may delay delivery for battery management. Reboot, clock/timezone changes and app startup renew scheduling. A notification action checks the current cycle before completing a task. No internet permission, account, cloud integration or automatic system backup is part of the application.

`AlarmManager.setAndAllowWhileIdle` schedules one inexact alarm; no exact-alarm permission is requested. Delivery rereads the database and settings and rejects a stale time/day. Completion, delivery and conditional notification dismissal share the store mutex. A newer summary cannot be erased by an older single-task action. A scheduling failure after a committed write is reported separately from a storage failure, so retry does not duplicate the mutation. The test notification has a separate identifier and never creates fake tasks.

Manual JSON export/import uses the iOS version-1 format. Validate the whole file before applying an atomic, add-only import; preserve existing IDs and regenerate imported cycle tokens. Documents are limited to 10 MiB and 10,000 tasks. User-chosen file providers may offer remote locations; Taskomatic itself implements no cloud save.

The document reader stops after at most 10 MiB + 1 byte even when a provider gives no size. Export validates/encodes before opening the output document; a provider write failure may leave an incomplete export, reported in the UI. The in-memory import preview survives rotation but is deliberately not persisted across process death: the user reselects the file, and no import occurs without confirmation.

`core/src/test/resources/ios-v1.json` was generated by the real Swift `TaskBackup.encoded()` implementation at iOS checkout `0e8a3b0`. The compatibility test writes `core/build/verification/android-v1.json`; delivery verification decoded that Kotlin output with the Swift implementation and compared every field, including the export date. The fixture is synthetic and contains no personal task data.
